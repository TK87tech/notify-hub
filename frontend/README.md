# Notify Hub frontend

React 19 + TypeScript + Vite, on Tailwind v4 with the shadcn component kit (Base UI,
not Radix) and a contract-generated API client.

## Getting started

```bash
npm install
npm run dev
```

The API base URL and the VAPID public key come from `VITE_API_URL` and
`VITE_VAPID_PUBLIC_KEY`; `VITE_SOCKET_URL` is optional and defaults to the API
host. Copy `.env.example` to `.env` to set them.

| Script | What it does |
| --- | --- |
| `npm run dev` | Dev server with HMR |
| `npm run build` | Typecheck, then production build |
| `npm run typecheck` | `tsc -b`, no emit |
| `npm run lint` | ESLint |
| `npm test` | Full Vitest suite, single run |
| `npm run test:watch` | Vitest in watch mode |
| `npm run api:types` | Regenerate `src/api/schema.d.ts` from the contract |
| `npm run api:check` | Regenerate and fail if the committed file moved |

## Layout

```
src/
  api/         contract types, client, query hooks
  auth/        session provider
  components/
    layout/    app shell, page chrome
    shared/    components used by more than one feature
    ui/        shadcn kit - generated, do not hand-edit
  features/    per-feature logic, grouped by feature
  lib/         framework-free helpers
  pages/       one component per route
  push/        service worker registration
  realtime/    websocket provider
  routes/      router and route guards
  theme/       token contrast checking
  test/        shared render harness and jsdom stubs
```

Route components stay in `pages/`. Anything a route needs that is not rendering
goes in `features/<feature>/` — that is where `features/notifications` and
`features/preferences` keep their pure logic, so it can be tested without
mounting a page.

## Conventions

These are the rules the code is expected to hold to. Where one is enforced by a
test rather than by review, the test is named.

### Use the kit, and compose with `render`

`components/ui` is generated by shadcn. Do not hand-edit it — re-run the shadcn
CLI instead, so a later regeneration does not silently undo your change.

This kit is built on Base UI, so the composition prop is `render`, not Radix's
`asChild`:

```tsx
// Correct for this kit.
<SidebarMenuButton render={<NavLink to="/" />} />

// Wrong: `asChild` does not exist here and is passed through as a DOM attribute.
<SidebarMenuButton asChild />
```

### Colours come from theme tokens

No raw hex outside `src/index.css`. Use the semantic utilities — `bg-background`,
`text-muted-foreground`, `border-border`, `bg-primary` — or add a token.

Avoid literal Tailwind palette classes such as `text-emerald-600` for anything
that carries meaning. They do not change with the theme, so they sit at a fixed
contrast in dark mode. The notification type colours are `--status-info`,
`--status-success` and `--status-warning` for this reason.

Every token added to `:root` needs a matching value in `.dark`, and a mapping in
the `@theme inline` block to become a utility. `theme-contrast.test.ts` checks the
pairs against each other in both themes, so a token that cannot meet WCAG AA fails
the build instead of shipping.

### Dark mode is a class, not a media query

`ThemeProvider` in `main.tsx` puts `.dark` on `<html>`; `index.css` hangs the dark
token values off it. New UI has to work in both themes without a
`prefers-color-scheme` block of its own — the user can override the OS setting,
and a media query would ignore that.

### Shared components go in `components/shared`

Anything a second feature needs belongs there rather than copied. Duplicated
components drift, and the drift is invisible until the two disagree on screen.

### Types come from the contract

`src/api/schema.d.ts` is generated. Never hand-write an API interface — add the
field to `contracts/openapi.yaml`, then `npm run api:types`. CI runs
`npm run api:check`, so a stale committed file fails the build.

### Accessibility

Target WCAG AA. Two specifics worth repeating:

- Never use colour as the only signal. The notification row marks unread with
  weight as well as a background, and announces it with `sr-only` text.
- Icon-only controls need an `aria-label`. The theme button's name also carries
  the current selection, so it reads as "Theme: Dark" rather than just "Theme".

## Testing

Tests sit beside the source they cover. `test/render.tsx` renders with the real
providers and stubs `fetch`; use it for anything that talks to the API so you do
not re-implement auth and query wiring per test.

The bar for a test is a behaviour that would be hard to spot by clicking. Pure
helpers and the theme tokens are checked directly; components are checked through
what a user can perceive.
